Semi-sticky fading banner

A fixed section-nav banner that fades out three seconds after you stop scrolling and reappears on the next scroll. The scroll-spy half is implemented correctly — exactly one link carries aria-current="location" at a time, and it tracks the section you are reading.

The show/hide half is the naive version, and it is broken in the usual ways:

  • Once the fade finishes the banner gets display: none, so its three links leave the tab order. A keyboard user tabbing down the page simply loses them, and nothing but a pointer scroll brings them back.
  • Focus is not tracked: tabbing into a link while it is fading does not cancel the fade.
  • The banner overlays the headings it links to, so following one of its own links lands with the target obscured.
  • The fade ignores prefers-reduced-motion.

Intro

Scroll down and stop. After three seconds the banner fades away. Scroll again and it comes straight back — but only for a pointer or a scroll key. Try reaching it with Tab alone after it has gone.

The pattern shows up on documentation sites, long-form articles and marketing pages: the nav is useful enough to pin, but it eats vertical space, so it gets hidden whenever the reader looks idle. "Idle" is measured by scroll events only, which is exactly the assumption that excludes keyboard and screen reader users.

Note that the fade is driven by a setTimeout restarted on every scroll event, and the final display: none is applied from a transitionend listener. Reading a section slowly, without scrolling, counts as idle.

There is a second-order problem too. Because the hidden state is display: none rather than visibility: hidden or an offscreen transform, the links are removed from the accessibility tree entirely, not just made unclickable. A screen reader user navigating by landmark will find the banner's nav one moment and not the next, with no announcement either way.

Details

The active link is recomputed once per animation frame from getBoundingClientRect().top: the last section whose top has passed under the banner wins, falling back to the first section at the very top of the page.

The banner offset used for that comparison is measured once at startup. Measuring it live would read zero while the banner is hidden, which would move the threshold every time it faded and flip the current link with no scrolling at all.

aria-current is only rewritten when the active section actually changes. Setting it every frame would be correct in the DOM but would give some screen readers a reason to re-announce the link repeatedly while scrolling.

Click "Summary" in the banner and watch where the page lands: the heading ends up underneath the banner, because there is no scroll-margin-top on the sections. That is left in on purpose.

The banner is position: fixed rather than sticky. A sticky banner is in normal flow, so collapsing it with display: none would remove its height, shift the content up, and fire another scroll event — which would show the banner again, shift everything back, and oscillate.

Summary

Things a fixed version would need: keep the banner reachable when hidden (translate it offscreen and bring it back on focusin, rather than removing it from the tree), cancel the fade while focus is inside it, respect prefers-reduced-motion, and add scroll-margin-top so its own links land on visible headings.

None of that is implemented here. Point a screen reader or one of this playpen's bookmarklets at the page and watch the banner's nav landmark come and go.
